## 1. Patch/manager ordering — claude-web, gemini-web, kimi-web, grok-web

HIGH. This one silently ate real work for hours.

A model told to use the patch grammar writes "apply this patch, then run this
to check it" — a `*** Begin Patch` block AND a ```powershell fence in one
reply. In these four vendors `parseManagerBlocks` still runs BEFORE
`parsePatchBlocks`. It extracts the shell fence as a `run_commands` call and
returns immediately, so the patch is never parsed: only the verification
command runs, against a file that never changed. The model then reports the
patch tool is broken and resends forever.

Fixed already in chatgpt-web — copy that shape exactly. In
`parseCapturedReply` (sdk/packages/llms/src/providers/vendors/chatgpt-web.ts,
near the top, look for the comment "Patch blocks are read BEFORE"):
  - run `parsePatchBlocks(text, toolNames)` first, keep `patchCalls`
  - run `unappliedPatchNotice(text, toolNames)` and return early if it fires
  - feed `patched.cleanedContent` to `parseManagerBlocks`
  - merge as `[...patchCalls, ...manager.delegations]` so the patch applies
    before the verification command, which is the order the model asked for
  - add a patch-only return before the `parseDeepSeekToolCalls` chain

kimi-web and grok-web have TWO parse sites each (the retry loop and
`buildCompletionFromText`); the other two have one.

WATCH OUT: a Python/bash edit script matching "\\t\\tconst patched" will also
match inside a three-tab line, because it is a substring. Anchor on full lines.

Verify: the regression test in
`tool-pipeline/patch-block.test.ts` ("a patch alongside a verification
command") covers the parser; for the vendors, re-read the diff by eye.
